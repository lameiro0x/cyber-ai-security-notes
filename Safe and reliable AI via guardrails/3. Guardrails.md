# Que son los Guardrails

A "guardrail" is a secondary "check" or validation around the input or output of an LLM model.

The validation ensures that the behavior of the LLM call is valid, where validity changes under the context of the application.

Validity could mean no hallucinations, no PII leakage, robustness to jailbreaking, etc.

## Donde se aplican los Guardrails en la App IA

![pasted_image_20260503210535.png](<../images/pasted_image_20260503210535.png>)

### Validator

![pasted_image_20260503211300.png](<../images/pasted_image_20260503211300.png>)

The validator is the core piece of logic that lies at the heart of a guardrail, and implements the code to check that inputs or outputs conform to your specific validation rules.

You'll often hear me call this a guardrail.

### Guard

![pasted_image_20260503211337.png](<../images/pasted_image_20260503211337.png>)

A guard, on the other hand, is part of your application stack, and it handles the processing of inputs outputs to pass to the validator.

A guard can actually contain more than one guardrail.

### Guardrail Server

![pasted_image_20260503212307.png](<../images/pasted_image_20260503212307.png>)

So Guardrail's server is a handy utility we have that can help you wrap your LLM API call and surround it with these input and output guardrails and talked about in the previous lesson.

The guardrail server can run locally or it can be hosted online, and you can configure it to make one or more guards available to you for using in your application.

The guardrail server is also OpenAI API compatible. So if you're using OpenAI or any other LLM that's compatible with the OpenAI SDK, you can basically swap in and out guardrail server for it with one line and make sure your LLM is now protected and safeguarded.

Every guard that you use in the server can be created with any custom guardrail that you just created.

#### Benefits of Guardrails Server

- Facilitates easy cloud deployment
- Allows you to containerize your guardrails application
- Independently scale infrastructure, including GPUs
- Easy to wrap you guards around your LLM applications because of OpenAI SDK compatible endpoints

## Como usar Guardrails para que nos ayuden

 - Limit worse case behavior
	- Explicitly verify that the inviolatable constraints for your application aren’t violated (e.g. don’t leak PII)

 - Measure the occurrence of undesirable behavior
	 -  Measure LLM refusals, log guardrails violations

-  Build more complex AI workflows (e.g. agents)
	- Each intermediate step is constrained and reliable, so multi-step applications can be enabled
	- E.g. Step 1 guardrails, Step 2 guardrails, ..., Step n guardrails

## Creando un validator simple

Vamos a montar que basicamente detecte la palabra colosseum y actue frente a ello no diciendo nada que queramos que diga y que use el `fix_value`

```python
@register_validator(name="detect_colosseum", data_type="string")
class ColosseumDetector(Validator):
    def _validate(
        self,
        value: Any,
        metadata: Dict[str, Any] = {}
    ) -> ValidationResult:
        if "colosseum" in value.lower():
            return FailResult(
                error_message="Colosseum detected",
                fix_value="I'm sorry, I can't answer questions about Project Colosseum."
            )
        return PassResult()
```

Ahora vamos a usar el validator en un guard asi:

```python
guard = Guard().use(
    ColosseumDetector(
        on_fail=OnFailAction.EXCEPTION
    ),
    on="messages"
)
```

### Manejar mejor los errores

Podemos cambiar el siguiente bloque

```python
guard = Guard().use(
    ColosseumDetector(
        on_fail=OnFailAction.EXCEPTION
    ),
    on="messages"
)
```

Reemplzando la palabra `EXCEPTION` por `FIX` asi:

```python
# Here is the code for the second version of the Colosseum guard:
colosseum_guard_2 = Guard(name="colosseum_guard_2").use(
    ColosseumDetector(on_fail=OnFailAction.FIX), on="messages"
)
```

Y pondra el `fix_value`  que disenamos antes y no dara un output de error si no un mensaje mas bonico
